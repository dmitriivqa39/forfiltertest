Self-test

Verifies the detector itself without AdGuard Extra installed: loads the official AdGuard Extra userscript into a hidden, isolated frame and runs the same checks there. The current page is not modified.

How it works

CheckWhat it looks forStrength
Extra core globals Top-level declarations from the AdGuard Extra userscript: shouldRunExtra, takeDomainsBlob, isTinyShieldAllowedForCurrentPage and others. Strong
TinyShield globals Internal TinyShield functions bundled into AdGuard Extra: EnableTinyShield, CreateTinyShieldController, Install*Patch. Strong (a group)
pageCallback$*, _0x* Many top-level helpers specific to the obfuscated AdGuard Extra bundle. Indirect
Inline script An inline <script> whose text contains AdGuard Extra markers. Strong, if present
Function.prototype.toString TinyShield fakes native code for functions named toString, get or set. Active check
Map.get, Map.set TinyShield proxies these methods and stringifies arguments; a native Map never calls toString on a key or value. Active check
setTimeout Proxy trap frame in the stack when the timer stringifies its argument. Active check
Why globals? AdGuard apps inject userscripts into the page world as a script. Its top-level function declarations become properties of window. AdGuard Extra itself acts only on domains from its own list, so on other sites it is inert — the leaked declarations are the only trace it leaves. On this build that is @version 1.1.41.

If a userscript manager wraps the code in a sandbox (for example, some Tampermonkey modes), the globals will not appear. In that case the page reports “Not detected” or “Inconclusive”, and only the active TinyShield checks can reveal anything. Test with AdGuard Extra enabled and disabled to see both states.
